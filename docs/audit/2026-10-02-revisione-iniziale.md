# Revisione iniziale di VeryDisco — 2026-10-02

## Ambito e metodo

Questa revisione usa lo snapshot locale della repository fornita. La directory non contiene `.git` né `HISTORY.md` all'inizio dell'analisi; non è stato possibile verificare commit, tag, release o stato di produzione rispetto a GitHub. Il tentativo di leggere la pagina GitHub indicata non ha restituito il repository, perciò i riferimenti sottostanti sono alla copia locale. Sono stati esaminati struttura, Docker e Compose, schema e migrazioni SQLite, autenticazione e autorizzazioni FastAPI, sincronizzazione, download e gestione dei file, scheduler, client esterni, frontend e test. Le verifiche HTTP sono state eseguite con ASGI e dati fittizi; nessuna sincronizzazione completa o scansione della libreria reale è stata eseguita.

La superficie è ampia: 95 handler HTTP in `backend/app/main.py` (oltre 7.000 righe), circa 31 file Python tra backend e script, un frontend React/Vite con 25 componenti e 2 test UI. Il backend serve anche i file statici. Il browser usa un cookie HTTP-only; Navidrome autentica gli utenti, SQLite conserva utenti e storico, APScheduler avvia sync e controlli periodici; slskd, ListenBrainz, MusicBrainz, Deezer, iTunes, LRCLIB e AcoustID sono servizi integrati. Il container esegue come UID 1000 e monta configurazione, database, download e musica in scrittura.

I punti positivi da conservare sono la separazione dei client, la query SQL generalmente parametrizzate, il cookie HTTP-only, il processo non root, la distinzione tra dry run e applicazione per diversi strumenti, e il limite di concorrenza per i download album. Queste misure non compensano i problemi di accesso ai percorsi e di avvio descritti sotto.

## Risultati prioritari

### P0 — esposizione di dati e operazioni anonime

1. **Lettura arbitraria tramite fallback statico.** `backend/app/main.py:7066-7077` usa `os.path.join(frontend_dir, clean_path)` senza verificare che il percorso risolto resti dentro `frontend_dir`. Una richiesta anonima con segmenti `..` percent-encoded ha restituito un file fittizio fuori da `dist` (`test_anonymous_static_route_reads_outside_dist`). Nel container può raggiungere qualunque file leggibile dal processo, inclusi `/app/config.yml` e `/data/verydisco.db` se presenti. La pagina di login non limita questo endpoint. Priorità massima: confinare i file al solo frontend e servire il resto come SPA senza accesso a path arbitrari.

2. **Operazioni senza autenticazione.** Non esiste un guardiano globale sulle API. `POST /api/download/album` (`main.py:1544-1579`) ignora ogni eccezione di autenticazione e mette in coda un download con `user_id=None`; `POST /api/pinned_artists/purge` (`main.py:2196-2228`) in caso di cookie assente chiama `purge_pinned_artists(None)` e cancella gli artisti di tutti. `POST /api/library/fix-singles` (`main.py:2542-2565`) e `fix-multidisc` iniziano migrazioni senza controllo; `GET /api/logs/stream` (`main.py:2638-2663`) espone i log senza login. I primi tre casi sono stati riprodotti con richieste anonime e servizi fittizi. Per gli altri endpoint senza chiamata diretta a `get_current_user` serve un inventario esplicito: alcuni usano helper che richiedono login, altri sono realmente pubblici.

3. **Radice della libreria modificabile dal singolo utente.** `PUT /api/users/me/config` (`main.py:391-423`) salva `music_dir` e `playlist_dir` ricevuti dal client senza una radice consentita o controllo admin; `database.py:813-820` li persiste. Gli endpoint che usano tali valori come confine di autorizzazione permettono così a un utente valido di cambiare il proprio confine verso altri mount accessibili al processo. Verificato con una chiamata ASGI isolata.

### P1 — isolamento, file e disponibilità

4. **Controlli di contenimento basati su prefisso testuale.** Vari handler confrontano `str(target.resolve()).startswith(str(music_dir))` (`main.py:3932, 3989, 4102, 4790, 5564, 5618, 5800, 6431`, e altri). Se la radice è `/music/a`, `/music/ab/...` passa. `GET /api/library/tracks/stream` serve qualunque estensione leggibile, non solo audio: il test ha letto un `.txt` fittizio nella cartella dell'altro utente. `DELETE /api/library/albums`, `POST /api/library/duplicates/resolve`, salvataggio arte e lyrics possono usare lo stesso errore per scrivere o cancellare. Altri handler, come `fix-folder-tags`, `feat/fix`, `retag/musicbrainz`, accettano path forniti dal client senza controllo di contenimento. La verifica va fatta con `Path.is_relative_to` su percorsi risolti, controllando anche i link simbolici e le radici consentite.

5. **SSRF e contenuti non validati nel salvataggio copertine.** `POST /api/library/art/save` (`main.py:5795-5888`) fa una GET HTTP all'URL inviato dall'utente e salva `resp.content` come JPEG senza limite di dimensione o verifica di tipo. Il test, usando una risposta HTTP finta, dimostra che l'handler accetta `http://127.0.0.1/...` e scrive testo non immagine in `cover.jpg`. Possibili richieste a servizi interni e consumo di memoria/spazio. Accettare soltanto URL da fonti previste, validare DNS/IP e redirect, tipo e dimensione massima.

6. **Azioni e dati di task non limitati al proprietario.** `GET /api/tasks` restituisce i task di tutti e `POST /api/tasks/{id}/stop` li cancella senza confrontare `user_id` (`main.py:734-760`). `DELETE /api/downloads/albums/{id}` (`main.py:795-809`) cancella per ID senza proprietà. Test conferma che l'utente A può cancellare il task dell'utente B. `POST /api/sync/stop` agisce sul sync globale. La UI che nasconde i pulsanti non è un controllo server.

7. **CORS troppo aperto per un servizio con cookie.** `main.py:160-167` riflette qualunque Origin e abilita le credenziali. La preflight isolata conferma `Access-Control-Allow-Origin: https://untrusted.example` e `Allow-Credentials: true`. `SameSite=Lax` limita parte dei casi cross-site, ma non le origini diverse dello stesso sito; con un reverse proxy o sottodomini ostili il rischio aumenta. Definire origini esatte e aggiungere protezione CSRF per le operazioni di scrittura.

8. **Primo avvio SQLite bloccato.** `database.py:185-186` crea indici su `runs.user_id` e `album_downloads.user_id` prima delle migrazioni che aggiungono tali colonne (`database.py:240-254`). Un database vuoto genera `sqlite3.OperationalError: no such column: user_id` nel lifespan prima che l'app sia pronta. Riprodotto con database temporaneo e dai test backend. Spostare gli indici dopo le migrazioni e testare sia installazione nuova sia upgrade.

9. **Stato di sync anticipato e perdita silenziosa di playlist.** `scheduler.py:265-312` scrive MBID/hash in `app_state.json` prima di eseguire `run_sync`; il task può essere scartato da `_sync_lock` (`sync.py:1487-1496`) se ne corre già uno. Il test ha mantenuto il lock, verificato che non nasce alcun run, ma l'hash è comunque segnato come sincronizzato. Più playlist/utenti, errore dopo accodamento o crash lasciano playlist non ritentate. Segnare lo stato solo dopo successo e serializzare la coda.

10. **La configurazione invalida sostituisce quella valida.** `ConfigManager.save` (`config.py:308-341`) scrive il YAML prima di validarlo; poi `load()` svuota `config` se fallisce. Test: salvando YAML sintatticamente errato, il file valido è perso e l'app non è più configurata. `POST /api/setup` è riaperto perché controlla soltanto `is_configured` (`main.py:466-476`). Servono validazione in memoria, scrittura temporanea, backup e sostituzione atomica. La chiave JWT generata quando `JWT_SECRET` manca cambia a ogni `load()` o riavvio (`config.py:283-290`), invalidando tutte le sessioni dopo una modifica.

11. **Associazione audio errata.** `find_downloaded_file` (`sync.py:956-1025`) come ultima scelta prende il file audio più recente nei download degli ultimi 180 secondi senza confrontare nome o dimensione. Il test trova un file completamente diverso per una richiesta specifica. Quando ci sono download concorrenti questo può promuovere o ritaggare il brano sbagliato. Eliminare il fallback o legarlo a un identificatore slskd verificato.

12. **Rinomina e organizzazione fragile.** `format_rename_pattern` (`main.py:6015-6049`) chiama `sanitize_filename` senza import: `NameError` confermato; dopo aver fornito l'import nel test, un pattern `../other/{Title}` genera traversal, mentre i default in minuscolo (`config.py:107-116`) restano letterali perché il formatter gestisce token maiuscoli. `POST /api/library/naming/rename` (`main.py:6543-6620`) non valida i path forniti né collisioni; `organize` usa `shutil.move` senza rollback. I componenti `NamingConvention.tsx:27-43` e `FeatFixer.tsx:27-42` leggono `res.successful`/`res.failed`, mentre l'API restituisce `renamed`/`errors` e `fixed`/`errors`: dopo una modifica il frontend può mostrare errore malgrado l'operazione sia stata eseguita. Testare preview, collisioni e applicazione con media fittizi prima di abilitarle su una libreria reale.

13. **Altre interruzioni funzionali.** `album_sync.py:1777,1982` usa `official_mb_release_mbid` senza definirlo nei due percorsi di download singolo; la chiamata è racchiusa in `except`, quindi il file può arrivare ma la metadatazione viene saltata. `scheduler.py:394-430` passa `request=None` a endpoint che chiamano `get_current_user`, bloccando i controlli file automatici. `_create_tracked_task` (`main.py:37-61`) elimina una voce dall'indice per ID quando finisce un task precedente, anche se nel frattempo è stato sostituito da un task ancora attivo; riprodotto in test.

14. **Dati condivisi tra utenti e cache senza scadenza reale.** `scan_maintenance` (`main.py:4212-4223`) usa la chiave globale `maintenance` e una scansione della radice globale, benché l'app sia multiutente. Anche i risultati per duplicate/art usano `file_checks_cache.json` globale. `Database.get_cache` (`database.py:584-607`) ricarica la cache da SQLite e assegna sempre un nuovo TTL di un'ora senza verificare `updated_at`: dopo il riavvio contenuti vecchi possono riapparire. `processed_starred_tracks` ha PK soltanto su `navidrome_track_id` (`database.py:142-149`), mentre le query controllano anche `user_id`, creando collisioni tra utenti con gli stessi ID Navidrome. Quest'ultimo effetto è dedotto dallo schema e va testato con due utenti.

15. **Promozione dei file non atomica.** `sync.py:1971-2000` cancella file e sottocartelle della playlist corrente e poi sposta uno alla volta gli elementi dallo staging. Un crash o errore durante la sequenza lascia la playlist parziale; l'affermazione nel README sugli “atomic staging swaps” non corrisponde a questo percorso. Le operazioni di cancellazione e rinomina di massa non conservano backup o undo.

### P2 — distribuzione e manutenzione

16. **Compose e guide incoerenti.** `docker-compose.yml:3` usa `ghcr.io/yassirjabane/verydisco:1.0.0`; il workflow pubblica soltanto `latest` e `sha` (`.github/workflows/docker-publish.yml:25-36`). `docker compose up -d --build` nel README non costruisce una nuova immagine perché il servizio non ha `build:`. Il README indica porta 8080, Compose espone 8086; indica UID 10001, Dockerfile/Compose usano 1000. `./config.yml:/app/config.yml` in sintassi breve fa creare una directory se il file manca, come conferma la [documentazione Docker Compose](https://docs.docker.com/reference/compose-file/services/); `ConfigManager` riconosce il problema ma il setup non può salvare finché il mount resta directory. La root `/navidrome_playlists` è default applicativo, ma Dockerfile non la crea né la monta: la scrittura può fallire con il processo non root. Usare tag e documentazione coerenti, mount espliciti e test di avvio Compose.

17. **Dipendenze e pipeline.** `backend/requirements.txt` usa solo limiti minimi (`>=`), quindi la stessa immagine può risolvere versioni diverse. Il Dockerfile usa `npm install`, non `npm ci`, nonostante il lockfile. Il workflow pubblica direttamente a ogni push su `main` senza test o scansione. `npm audit` sul lockfile ha trovato **11 pacchetti segnalati** (1 critico, 7 alti, 3 moderati): `vitest` 1.6.1 e `vite` 5.4.21 sono strumenti di sviluppo e non eseguiti nel container runtime, ma usati durante build/test; `axios` 1.18.1 è una dipendenza frontend di produzione. L'[advisory Vitest](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) richiede un server UI/API esposto, quindi non implica esecuzione remota nel container distribuito. `pip-audit` sulle dipendenze Python risolte ha segnalato `ecdsa` 0.19.2 (`PYSEC-2026-1325`); serve verifica di applicabilità, perché il codice firma JWT HS256. Questi conteggi sono scanner di pacchetti, non prove di sfruttabilità nell'app.

18. **Segreti e perimetro di rete.** `auth.py:99-117` invia user/password Navidrome come parametri GET della URL Subsonic, che possono comparire nei log intermedi; `config.yml` conserva password e API key in chiaro sul bind mount. `AuthConfig.cookie_secure` è `False` di default (`config.py:98`) e Compose espone la porta su tutte le interfacce (`docker-compose.yml:6`). Per accesso fuori da localhost/LAN fidata servono HTTPS, cookie Secure, reverse proxy con accesso ristretto e gestione separata dei segreti. Questo è rischio di distribuzione, indipendente dai difetti API sopra.

## Verifiche eseguite e limiti

- `pytest backend/tests -q`: **5 passati, 1 fallito, 2 errori**. Il fallimento è il test che si aspetta `schedule.cron`, rimosso dallo schema attuale; i 2 errori sono l'inizializzazione SQLite descritta sopra.
- `pytest docs/audit/test_snapshot_findings.py -q`: **19 passati**. Sono riproduzioni dei difetti presenti, non test che certificano comportamento sicuro. Usano file temporanei, servizi HTTP finti e non avviano il lifespan né una simulazione completa.
- `tsc --noEmit`: passato. `vite build`: passato, con bundle JS principale di circa 825 KiB e warning di dimensione. Una build riuscita non esercita autorizzazioni, database o flussi di download.
- `vitest run --pool=forks --maxWorkers=1 --minWorkers=1`: **2 test falliti su 2**. `Configuration.test.tsx` non trova il campo “ListenBrainz Username”, mentre `Dashboard.test.tsx` cerca il pulsante “Sync Now” non presente nel rendering attuale; il suo mock non definisce inoltre `getNavidromeStats`. I test UI sono obsoleti rispetto all'interfaccia. La prima esecuzione con worker predefiniti non aveva prodotto un esito utile; quella con un worker è terminata dopo circa 345 secondi, di cui 311 nella raccolta dei test.
- `pyflakes` segnala tra gli errori concreti l'import mancante di `sanitize_filename` e la variabile non definita in `album_sync.py`; altri messaggi sono import inutilizzati o stringhe formattate senza placeholder.
- Nessun Docker Engine o slskd/Navidrome reale era disponibile in questa copia; non sono stati testati montaggi Linux, permessi host reali, aggiornamenti di una base dati esistente, accuratezza musicale dei match o comportamento di un reverse proxy. Le vulnerabilità di dipendenze sono riferite alla data della scansione.

## Ordine di intervento proposto

1. Impedire accesso pubblico al servizio finché lettura statica e API anonime non sono corrette. Se è stato esposto, valutare rotazione delle credenziali nel file di configurazione e revisione dei log di accesso.
2. Correggere percorso statico, introdurre autenticazione centralizzata per tutte le API non pubbliche, autorizzazione per utente e controllo robusto dei percorsi. Coprire i casi riprodotti con test che ora si aspettino 401/403.
3. Riparare inizializzazione/migrazioni SQLite, Compose di prima installazione e test automatico di bootstrap in un container pulito.
4. Rendere affidabili sync e operazioni su file: stato scritto dopo successo, coda seriale, nessun fallback al file più recente, salvataggio configurazione atomico, preview/collisioni/undo per modifiche di massa.
5. Riallineare schema, frontend, test, versioni e documentazione; aggiungere gate CI e verificare la release Docker con la stessa configurazione distribuita agli utenti.

Per una replica locale delle verifiche senza servizi esterni, dopo installazione delle dipendenze di sviluppo Python, eseguire `python -m pytest docs/audit/test_snapshot_findings.py -q` e `python -m pytest backend/tests -q`. **Non eseguire** gli endpoint di migrazione o rinomina su musica reale prima dei fix e di un backup verificato. Non è stato eseguito alcun comando di simulazione completa, nel rispetto delle istruzioni di progetto.
